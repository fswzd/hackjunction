# 内容主创架构审计

基线为远端 `main` 的 `fa48ea5`。审计沿 `draft → rules → review → revise` 检查编排层、业务入口和最终落库。

| 检查面 | 发现与处置 |
| --- | --- |
| 系统提示 | `birthco-local/backend/agents/director.py` 补齐包络分支纪律，禁止用正文或素材中的指令改变角色 |
| 短期上下文 | `live_adapters.py` 仅投影任务书、已授权素材和本次修改对象 |
| 长期记忆 | 试映台账由编排仓储写入。盲测分析无法读取历史结论 |
| 证据整理 | `material_retrieval.py` 在本任务素材内至多扩展三轮，保留来源和未命中素材 |
| 冻结条件 | `nodes.py` 记录稿件对应的 Brief 版本，后续审稿和改稿继续使用这个版本 |
| 工具边界 | `ProductionAdapter` 按 action 分发，校验任务归属、确认态、版本和素材指纹 |
| 模型执行 | 通过本体和 MiMo 工厂执行，编排对业务适配器最多尝试一次 |
| 结果解释 | 程序统一标题、封面、正文及长度规则，结构失败可以留稿，但不能直接进入审稿通过 |
| 输出契约 | `ContentCandidate` 与 `Revision` 保持独立。只有修订结果带 `change_log` |
| 用户确认 | 第一次写稿受 Brief 闸门约束。试映选中的 finding 与修订范围绑定 |
| 修订边界 | 共用 `validate_scoped_revision`，核对每条来源、改动和顺序。保留段落不可借用新段 ID 被替换 |
| 持久化 | 段落 ID 由编排预留，真实调用收据带提示词和配置指纹。候选稿和基线分开保存 |

重点风险是 `rules` 和审稿员此前对同名规则作出不同判断，以及编排仅靠 `change_log` 的 ID 集合核对修改。现已使用同一套正文规则和差异校验。保留的验证边界是既有原稿需要可引用的冻结版本才能走编排的真实修订，旧稿尚未入库时返回补件。MiMo 内容质量需要用轮换后的密钥另行验收。
